# 大模型微调（Full SFT）完整流程解析

> 基于 MiniMind 项目的 `trainer/train_full_sft.py` 进行逐步拆解。
> 建议先阅读「预训练完整流程」，本文会重点突出微调与预训练的**差异点**。

---

## 一、总览：微调到底在做什么？

预训练让模型学会了"语言能力"（给定前文预测下一个字），但它还不会"听话"——你问它问题，它可能接着你的话继续瞎编，而不是像助手一样回答。

**SFT（Supervised Fine-Tuning，监督微调）就是教模型"听话"**：给它看大量"用户提问 → 助手回答"的对话样本，让它学会按照对话格式来回复。

```
预训练模型的行为（续写）：
  用户：北京的天气怎么样？
  模型：北京的天气怎么样呢？其实这个问题要从多个角度来看...（无限续写）

SFT 后模型的行为（对话）：
  用户：北京的天气怎么样？
  助手：今天北京晴，气温 15-25℃，适合外出。
```

### 预训练 vs 微调的核心区别

| 维度 | 预训练（Pretrain） | 微调（Full SFT） |
|------|-------------------|-----------------|
| **目标** | 学习语言能力 | 学习对话/指令遵循能力 |
| **数据格式** | 纯文本 `{"text": "..."}` | 多轮对话 `{"conversations": [...]}` |
| **Labels 策略** | 所有 token 都参与 loss | **只有助手回复部分参与 loss** |
| **初始权重** | 随机初始化（或从更早的权重继续） | 从预训练权重开始 |
| **学习率** | 较大（5e-4） | **很小（1e-6）**，避免破坏已学到的知识 |
| **梯度累积** | 8 步 | **1 步**（SFT 数据量小，不需要模拟大 batch） |
| **训练轮数** | 通常 1 轮 | 通常 2+ 轮 |
| **模型结构** | 不变 | **完全不变**（Full SFT 更新所有参数） |
| **训练循环** | 几乎一样 | 几乎一样 |

> **核心洞察**：训练循环（forward → backward → update）和预训练完全一样，微调的本质区别在于**数据怎么处理**和**哪些 token 参与 loss**。

### 第 5 步：创建模型 + 数据集 + 优化器（核心差异）

#### 5.1 模型初始化：加载预训练权重

```python
model, tokenizer = init_model(lm_config, args.from_weight, device=args.device)
```

**关键差异**：`from_weight` 默认值不同。

```python
# 预训练：默认从零开始
parser.add_argument('--from_weight', default='none')

# 微调：默认加载预训练权重
parser.add_argument('--from_weight', default='pretrain')
```

`init_model` 内部会加载 `out/pretrain_512.pth` 作为初始权重：

```python
def init_model(lm_config, from_weight='pretrain', ...):
    model = MiniMindForCausalLM(lm_config)
    if from_weight != 'none':
        weight_path = f'{save_dir}/{from_weight}_{lm_config.hidden_size}.pth'
        weights = torch.load(weight_path, map_location=device)
        model.load_state_dict(weights, strict=False)  # strict=False 允许部分匹配
    return model.to(device), tokenizer
```

> **为什么用 `strict=False`？** 预训练保存的权重文件可能和当前模型结构不完全匹配（比如 MoE 配置变了），`strict=False` 允许只加载能匹配上的参数，忽略不匹配的。

#### 5.2 SFT 数据集（最核心的差异）

```python
train_ds = SFTDataset(args.data_path, tokenizer, max_length=args.max_seq_len)
```

##### SFT 数据格式

预训练数据是纯文本，SFT 数据是**多轮对话**：

```json
{
  "conversations": [
    {"role": "system", "content": "你是一个有用的助手"},
    {"role": "user", "content": "北京的天气怎么样？"},
    {"role": "assistant", "content": "今天北京晴，气温15-25℃。"},
    {"role": "user", "content": "需要带伞吗？"},
    {"role": "assistant", "content": "不需要，今天没有降水预报。"}
  ]
}
```

##### SFTDataset 的完整实现

```python
class SFTDataset(Dataset):
    def __init__(self, jsonl_path, tokenizer, max_length=1024):
        self.tokenizer = tokenizer
        self.max_length = max_length
        self.samples = load_dataset('json', data_files=jsonl_path, split='train')

        # 预编码"助手回复"的开始/结束标记序列，用于 labels 的掩码定位
        self.bos_id = tokenizer(
            f'{tokenizer.bos_token}assistant\n',      # "<|im_start|>assistant\n"
            add_special_tokens=False
        ).input_ids
        self.eos_id = tokenizer(
            f'{tokenizer.eos_token}\n',               # "<|im_end|>\n"
            add_special_tokens=False
        ).input_ids
```

> **bos_id / eos_id 的用途**：在 token 序列中搜索这两个子序列，就能定位出"助手回复"的起止位置。

##### 第一步：用 chat_template 将对话格式化为字符串

```python
def create_chat_prompt(self, cs):
    messages = cs.copy()
    # 检查是否有 function calling 工具定义
    tools = cs[0]["functions"] if (
        cs and cs[0]["role"] == "system" and cs[0].get("functions")
    ) else None
    return self.tokenizer.apply_chat_template(
        messages,
        tokenize=False,           # 只返回字符串，不做分词
        add_generation_prompt=False,
        tools=tools
    )
```

**chat_template 会将对话结构渲染成这样的字符串：**

```
<|im_start|>system
你是一个有用的助手<|im_end|>
<|im_start|>user
北京的天气怎么样？<|im_end|>
<|im_start|>assistant
今天北京晴，气温15-25℃。<|im_end|>
<|im_start|>user
需要带伞吗？<|im_end|>
<|im_start|>assistant
不需要，今天没有降水预报。<|im_end|>
```

> **chat_template** 是 HuggingFace tokenizer 提供的 Jinja2 模板，定义在 `tokenizer_config.json` 的 `chat_template` 字段中。它统一了不同模型的对话格式（ChatML 格式）。
>
> **前端类比**：就像 React 的 JSX 模板把数据渲染成 HTML，chat_template 把对话数据渲染成模型能理解的文本格式。

##### 第二步：构造 labels（只让助手回复参与 loss）

这是 SFT 与预训练**最本质的区别**。

```python
def generate_labels(self, input_ids):
    labels = [-100] * len(input_ids)  # 默认全部忽略
    i = 0
    while i < len(input_ids):
        # 搜索 "<|im_start|>assistant\n" 的 token 序列
        if input_ids[i:i + len(self.bos_id)] == self.bos_id:
            start = i + len(self.bos_id)  # 跳过标记本身
            end = start
            # 搜索对应的 "<|im_end|>\n"
            while end < len(input_ids):
                if input_ids[end:end + len(self.eos_id)] == self.eos_id:
                    break
                end += 1
            # 只有 start ~ end（含 eos）这段才设置 labels
            for j in range(start, min(end + len(self.eos_id), self.max_length)):
                labels[j] = input_ids[j]
            i = end + len(self.eos_id)
        else:
            i += 1
    return labels
```

**labels 掩码图解：**

```
token 序列：
<|im_start|> system \n 你是... <|im_end|> \n <|im_start|> user \n 北京... <|im_end|> \n <|im_start|> assistant \n 今天北京晴... <|im_end|> \n

labels：
  -100      -100  -100 -100  -100      -100 -100       -100  -100 -100   -100     -100  -100         -100     -100  今天北京晴... <|im_end|> -100

     ▲ system 部分全部 -100          ▲ user 部分全部 -100           ▲ "assistant\n" 标记也是 -100     ▲ 只有回复内容 + EOS 参与 loss
```

**更直观的标注：**

```
token:  [system部分] [user提问] [assistant标记] [助手回复内容] [EOS] [user提问2] [assistant标记] [助手回复2] [EOS] [PAD...]
labels: [-100 ....] [-100 ...] [-100 ........] [回复内容....] [EOS] [-100 ....] [-100 ........] [回复2....] [EOS] [-100..]
         ↑ 不计loss   ↑不计loss  ↑不计loss       ↑ 计算loss!    ↑计!   ↑不计      ↑不计          ↑计算loss!  ↑计!  ↑不计
```

> **为什么只对助手回复计算 loss？**
>
> 1. **system/user 部分是"输入条件"**，模型不需要"学会生成"这些内容，只需要理解它们
> 2. 如果对 user 部分也算 loss，模型会花精力学习"如何提问"，偏离了"学习如何回答"的目标
> 3. 这种策略叫 **Causal LM with selective loss masking**，是 SFT 的标准做法

##### 第三步：__getitem__ 组装完整样本

```python
def __getitem__(self, index):
    sample = self.samples[index]

    # 1. 对话 → 格式化字符串 → token ids
    prompt = self.create_chat_prompt(sample['conversations'])
    input_ids = self.tokenizer(prompt).input_ids[:self.max_length]

    # 2. padding 到固定长度
    input_ids += [self.tokenizer.pad_token_id] * (self.max_length - len(input_ids))

    # 3. 生成 labels（只有助手回复部分有值，其余为 -100）
    labels = self.generate_labels(input_ids)

    return torch.tensor(input_ids, dtype=torch.long), torch.tensor(labels, dtype=torch.long)
```

#### 5.3 超参数差异

```python
# ===== 微调的默认超参数 =====
parser.add_argument("--save_weight", default='full_sft')        # 权重保存前缀
parser.add_argument("--epochs", default=2)                       # 训练 2 轮（预训练 1 轮）

parser.add_argument("--learning_rate", default=1e-6)             # 学习率 1e-6（预训练 5e-4）
parser.add_argument("--accumulation_steps", default=1)           # 不累积（预训练 8 步）
parser.add_argument("--data_path", default="../dataset/sft_mini_512.jsonl")
parser.add_argument("--from_weight", default='pretrain')         # 基于预训练权重
```

**为什么学习率要小 500 倍？（1e-6 vs 5e-4）**

```
预训练：模型从零开始，参数随机 → 需要大步快跑 → lr = 5e-4
微调：模型已有丰富知识 → 只需微调方向 → lr = 1e-6

类比：
  预训练 = 从零学英语（大量输入，快速学习）
  微调   = 已会英语的人学商务邮件写法（小心调整，别把英语忘了）
```

> 如果微调时学习率太大，模型会"灾难性遗忘"——把预训练学到的语言能力丢掉，只记住 SFT 数据里的模式。

### 第 8 步：训练循环（与预训练完全一致）

训练循环的代码和预训练脚本几乎逐行一样，包括：
- 外层 epoch 循环 + SkipBatchSampler
- 内层 step 循环：数据搬运 → 学习率调度 → 前向传播 → 反向传播 → 梯度累积/裁剪/参数更新
- 日志打印 + 模型保存

```python
for epoch in range(start_epoch, args.epochs):
    train_sampler and train_sampler.set_epoch(epoch)
    setup_seed(42 + epoch)
    indices = torch.randperm(len(train_ds)).tolist()
    skip = start_step if (epoch == start_epoch and start_step > 0) else 0
    batch_sampler = SkipBatchSampler(train_sampler or indices, args.batch_size, skip)
    loader = DataLoader(train_ds, batch_sampler=batch_sampler,
                        num_workers=args.num_workers, pin_memory=True)
    train_epoch(epoch, loader, len(loader), 0, wandb)
```

#### train_epoch 内部（与预训练对比）

```python
def train_epoch(epoch, loader, iters, start_step=0, wandb=None):
    for step, (input_ids, labels) in enumerate(loader, start=start_step + 1):
        input_ids = input_ids.to(args.device)
        labels = labels.to(args.device)

        # 学习率调度（一样）
        lr = get_lr(epoch * iters + step, args.epochs * iters, args.learning_rate)

        # 前向传播（一样，但 labels 的内容不同！）
        with autocast_ctx:
            res = model(input_ids, labels=labels)
            loss = res.loss + res.aux_loss
            loss = loss / args.accumulation_steps

        # 反向传播（一样）
        scaler.scale(loss).backward()

        # 参数更新（一样）
        if (step + 1) % args.accumulation_steps == 0:
            scaler.unscale_(optimizer)
            torch.nn.utils.clip_grad_norm_(model.parameters(), args.grad_clip)
            scaler.step(optimizer)
            scaler.update()
            optimizer.zero_grad(set_to_none=True)
```

> **虽然代码一样，但因为 labels 不同，loss 的含义也不同**：
> - 预训练：loss 衡量模型预测所有 token 的能力
> - 微调：loss 只衡量模型生成"助手回复"的能力（其他位置被 -100 忽略）

## 五、Chat Template 详解

Chat Template 是 SFT 数据处理的关键环节，定义在 `model/tokenizer_config.json` 中。

### 5.1 特殊 token

| Token | ID | 含义 |
|-------|-----|------|
| `<\|im_start\|>` | 1 | 消息开始标记（同时是 BOS） |
| `<\|im_end\|>` | 2 | 消息结束标记（同时是 EOS） |
| `<\|endoftext\|>` | 0 | 填充/未知 token（PAD / UNK） |

### 5.2 ChatML 格式

MiniMind 使用的是 **ChatML** 格式（和 Qwen、ChatGPT 类似）：

```
<|im_start|>system
你是一个有用的助手<|im_end|>
<|im_start|>user
北京的天气怎么样？<|im_end|>
<|im_start|>assistant
今天北京晴，气温15-25℃。<|im_end|>
```

### 5.3 Template 的 Jinja2 逻辑（简化版）

```jinja2
{# 1. system 消息 #}
{% if messages[0].role == 'system' %}
  <|im_start|>system
  {{ messages[0].content }}<|im_end|>
{% else %}
  <|im_start|>system
  You are a helpful assistant<|im_end|>
{% endif %}

{# 2. 遍历所有消息 #}
{% for message in messages %}
  {% if message.role == "user" %}
    <|im_start|>user
    {{ message.content }}<|im_end|>
  {% elif message.role == "assistant" %}
    <|im_start|>assistant
    {{ message.content }}<|im_end|>
  {% endif %}
{% endfor %}

{# 3. 如果需要，加上生成提示 #}
{% if add_generation_prompt %}
  <|im_start|>assistant
{% endif %}
```

> 模板还支持 **function calling（工具调用）**：当对话包含 `tools` 字段时，会在 system 消息中插入工具描述，assistant 消息中支持 `<tool_call>` 格式。

### 5.4 SFTDataset 如何利用 chat_template 定位助手回复

```
格式化后的 token 序列中：

  ...<|im_start|>assistant\n 回复内容 <|im_end|>\n...
      ^^^^^^^^^^^^^^^^^^^^^^^^                ^^^^^^^^^
      self.bos_id                             self.eos_id
      （助手开始标记序列）                       （结束标记序列）

generate_labels 的逻辑：
  1. 在 token 序列中搜索 bos_id 子序列
  2. 从 bos_id 之后开始，搜索 eos_id 子序列
  3. 这段区间内的 labels = input_ids（参与 loss）
  4. 其余位置的 labels = -100（不参与 loss）
```

## 六、完整数据流对比

### 预训练数据流

```
jsonl: {"text": "今天天气真好"}
  │
  ▼
PretrainDataset:
  input_ids = [BOS] + tokenize("今天天气真好") + [EOS] + [PAD...]
  labels    = input_ids.clone()，PAD位 → -100
  │
  ▼
模型计算 loss：对所有非 PAD token 做 next-token prediction
```

### 微调数据流

```
jsonl: {"conversations": [
    {role: "user", content: "天气?"},
    {role: "assistant", content: "晴天"}
]}
  │
  ▼
SFTDataset:
  ① apply_chat_template → "<|im_start|>system\n...<|im_start|>user\n天气?<|im_end|>\n<|im_start|>assistant\n晴天<|im_end|>\n"
  ② tokenize → input_ids
  ③ generate_labels → 只有"晴天<|im_end|>"部分有标签，其余 -100
  │
  ▼
模型计算 loss：只对"助手回复"做 next-token prediction
```

### 模型内部（两者完全一致）

```
input_ids [B, T]
    │
    ▼
Embedding → [B, T, H]
    │
    ▼
Transformer Block × N
(RMSNorm → Attention → Add → RMSNorm → FFN/MoE → Add)
    │
    ▼
RMSNorm → lm_head → logits [B, T, V]
    │
    ▼
shift_logits = logits[..., :-1, :]   ← 去掉最后一个时间步
shift_labels = labels[..., 1:]        ← 去掉第一个位置
    │
    ▼
CrossEntropyLoss(ignore_index=-100)   ← -100 位置自动跳过
    │
    ▼
loss.backward() → clip_grad → optimizer.step()
```

## 七、关键超参数速查表

| 参数 | 默认值 | 与预训练对比 | 原因 |
|------|--------|-------------|------|
| `save_weight` | `full_sft` | 预训练是 `pretrain` | 区分不同阶段的权重 |
| `epochs` | **2** | 预训练 1 | SFT 数据量小，多训几轮 |
| `batch_size` | **16** | 预训练 32 | SFT 序列通常更长，减小 batch 省显存 |
| `learning_rate` | **1e-6** | 预训练 5e-4 | 小学习率防止灾难性遗忘 |
| `accumulation_steps` | **1** | 预训练 8 | SFT 不需要模拟大 batch |
| `data_path` | `sft_mini_512.jsonl` | 预训练 `pretrain_hq.jsonl` | SFT 用对话数据 |
| `from_weight` | **`pretrain`** | 预训练 `none` | SFT 从预训练权重继续 |
| `hidden_size` | 512 | 一样 | 模型结构不变 |
| `num_hidden_layers` | 8 | 一样 | 模型结构不变 |
| `max_seq_len` | 340 | 一样 | 截断长度 |
| `grad_clip` | 1.0 | 一样 | 梯度裁剪 |

## 九、Full SFT vs LoRA SFT

MiniMind 项目中还有一个 `model/model_lora.py`，实现了 LoRA 微调。两种微调方式的区别：

| 维度 | Full SFT（本文） | LoRA SFT |
|------|-----------------|----------|
| **更新参数** | 所有参数 | 只更新少量低秩矩阵 |
| **显存占用** | 大（需存所有参数的梯度和优化器状态） | 小（只存 LoRA 参数的梯度） |
| **训练速度** | 慢 | 快 |
| **效果上限** | 高（模型充分调整） | 略低（受限于低秩约束） |
| **适用场景** | 数据充足 + 算力充足 | 数据少 / 算力有限 / 快速实验 |

> Full SFT 适合"有足够算力和数据，追求最佳效果"的场景；LoRA 适合"快速实验、低成本微调"。

## 十一、小贴士（给前端开发者）

| SFT 概念 | 前端类比 |
|----------|---------|
| chat_template | React/Vue 组件模板（将数据渲染为结构化文本） |
| labels 掩码（-100） | CSS `visibility: hidden`（元素存在但不参与计算） |
| 预训练 → SFT | 先学 JavaScript 语言 → 再学 React 框架（在语言能力基础上学特定技能） |
| `from_weight='pretrain'` | `npm install`（先拿到基础依赖，再在上面开发） |
| 灾难性遗忘 | 升级依赖版本后旧功能 break（所以学习率要小，改动要温和） |
| Full SFT vs LoRA | 全量重构 vs 打补丁（Patch）|
| `strict=False` 加载权重 | TypeScript 的 `Partial<T>`（允许缺少部分字段） |
| 多轮对话 labels | 表单验证只校验用户填的字段，不校验 label 和 placeholder |
